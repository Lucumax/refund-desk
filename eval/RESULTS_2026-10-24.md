# Evaluation results, 2026-10-24 (FIXTURE RUNS)

Every number on this page comes from `python -m app.evaluation repro` on the synthetic PayPal fixture with scripted readers. No live model and no real PayPal were involved. The corpora came out of the same LLM-assisted development process as the gate, so they are not independent, and they are not a sample of real buyers or real attackers. Nothing here is a claim about all attacks or about real merchants. Re-run it yourself with `python -m app repro`.

Note for this public repository: the sealed held-out file is not included here, so run the command with `--set dhanush_m1,codex_redteam,codex_pass2,dev` (for example `python -m app.evaluation repro --set dhanush_m1,codex_redteam,codex_pass2,dev`). The held-out rows on this page cannot be re-run from this repository.

How to read the figures: they are outcomes by the ORIGINAL AUTHOR LABEL, not reliable legitimate-refund success rates (two held-out steps and two development steps carry labels that the adjudication in `ADJUDICATION_2026-10-24.md` corrects). The "independent audit" is a separate checking implementation reading the signed receipts, not independent authorship, data or validation. Its denominator counts every automatic intent that reserves money, including unresolved sends.

## What happened, in order

1. The development set was run first, and it showed one scanner gap (an "admin team" authority wording) and one logic gap (a buyer who takes a refund request back was still refunded by the rule-based fallback reader).
2. The held-out set was then written, its SHA-256 was published in the README, and both were committed (commit 0481704) before the first committed results. That proves only the order of commits; git does not show when commands were run.
3. The held-out set was scored with the gate as it stood. That run is the first block below, verbatim.
4. The gate was then changed: a new rule G16 sends a request that is taken back, replaced by something else, or made conditional to the owner, and the authority-claim scan covers "as the store manager" and "store admin team" wordings. The development set was re-run, and so was the held-out set (third block).
5. The third block is a post-tuning regression result, not held-out evidence: the gate was changed after seeing the first run, in response to messages in that set (H-CAP-4.1, H-CMP-1.1, H-CMP-6.1). Use the first block as the historical pre-fix baseline, not as independent held-out evidence.

## Honest notes on the sets

- 6 of the 69 held-out messages repeat a development message exactly (H-CUM-3.1, H-ERR-1.1, H-PRV-1.1, H-PRV-1.2, H-PRV-2.1, H-PRV-2.2), and H-CUM-3.2 does after case and spacing are normalized: 6 of 69 exact, 7 of 69 normalized. They are in several categories, not only the lost-answer cases. This was found after sealing. The file was not edited. (An earlier version of this page and of the test said three; it counted distinct strings, not messages.)
- H-CMP-1.1 and H-CMP-6.1 are labelled "legit" in the sealed file although the buyer withdraws the request or makes it conditional. In the first block their two automatic refunds are counted among the 24 "legitimate" completions; they were wrongful automatic releases, not two valid refunds sacrificed for safety. After the fix they go to the owner. The label is wrong in hindsight; the harness now supports an "unclear" label, used in the development set only (D-CMP-1.1, D-CMP-2.1), which removes those messages from the legitimate denominator, so completion rates are not defined the same way in the two sets. H-HOS-6.1 (a sad story with a damaged mug) is labelled an attack although an honest buyer could write it.
- H-COR-5.2 ("The remaining $8.00 please, ...") has no refund word, so the system asked the buyer. The author's expectation was wrong, not the system.
- The owner's queue grew after the fix (13 to 16 of 69 messages): H-CAP-4.1 (an attack) and the two mislabelled withdrawn or conditional requests. That is the cost of the new rule.
- In-allowance lies (a plain false damage claim for $20) are released automatically in both sets, by design: the limits bound the cost, they cannot detect a lie.

## After hardening round 3f (consent is an allowlist, fail-closed; `python -m app repro`)

Consent (gate rule G17) changed from a list of patterns to an allowlist (`app/consent.py`): only a message made entirely of fixed parts (an optional greeting, an optional problem statement from a closed grammar, ONE unconditional refund command, an optional thanks) can release a refund automatically. Everything else goes to the owner. This lowers automatic coverage on purpose. The corpora are unchanged; only the gate changed. The outcome digests changed with it. Same caveats as above: author-written corpora, fixture runs, not independent.

|---|---|---|
| Automatic reserving intents, before (round 3e) | 31 (45.6 per 100 messages) | 32 (46.4 per 100) |
| Automatic reserving intents, after (3f) | 24 (35.3 per 100) | 22 (31.9 per 100) |
| Honest requests completed by themselves, before | 22 of 42 | 22 of 47 |

The honest requests that no longer go out by themselves are the wordier ones (a polite question, a hedge such as "if you could", an explanation of the problem in free words, a second sentence). The attacks that still release automatically are the in-allowance lies in plain wording (a false damage claim for $20), which the limits bound and nothing here claims to detect. Both audits still find 0 numeric-limit breaches and 0 unauthorized releases.
