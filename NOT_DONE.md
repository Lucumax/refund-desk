## Design decisions
- Owner caps bound cumulative AUTOMATIC refunds per order, not each message or owner approvals.
- Daily budgets cover AUTOMATIC refunds only. Manual approvals face remaining-order balance and a hard per-refund ceiling, with no aggregate daily cap.
- Later FAILED refunds retain automatic budget until human resolution, potentially holding legitimate requests that day.
- No global anomaly tightening. Repeat/pressure signals escalate only that request; identical repeated messages are refused. Other buyers' limits stay fixed.
- Saving a policy version voids older approval cards. Owners must deny them; buyers must write again. No automatic reissue.
- Every rule has a readable gate sentence. Policy Builder uses fixed phrases, not a model.

## Known gaps
- Login: shared passcode, in-memory sessions, localhost HTTP; no real identity, roles or secure cookie flag. Non-expiring order-link tokens let holders impersonate buyers. In-memory throttling resets on restart.
- Checkpoints use a separate folder, normally the same disk. Restoring both ledger and an older consistent checkpoint escapes detection. Use `--checkpoint-dir` on another disk/service. Verify checks three signed chains: money, authority and policy. It detects changes against trusted checkpoints, not factual truth. Compromised signing keys are out of scope.
- Code is trusted; buyer text/model output are not. The reader shares the process and could read environment variables. Protection comes from `app/paypal_adapter.py` alone building refund calls, each preceded by a signed authority decision; there is no process isolation.
- Short English keyword/pattern scans miss rewordings. Order, amount, evidence and budget rules still apply. Evidence checks words, support and negation, not truth. Plausible dishonest requests within caps are released; limits bound cost.
- Scoreboards cover 20 library attacks, 3 ordinary messages, 11 desk scenarios (10 scripted readers, one fault demo), plus typed messages. They are not held-out or evidence about all attacks. Development/sealed evaluations (`eval/`, `docs/DETAILS.md` “Reliability evaluation”) use fixtures, not live models. Nobody other than the author labelled a case.
- Vendored core pre-dispatch failures record EXPIRED/BLOCKED, releasing reservations. Its subclass `app/holding_engine.py` keeps UNKNOWN held, ignores its authorization window and records `resend_refused`, outcome UNKNOWN. Execution and authorization windows start differently; policy changes can also invalidate authorization. Proposed core fix, outside this repository: UNKNOWN/SUBMITTING retries should only reconcile, never record EXPIRED.
- Dispatch holds the ledger lock. Slow PayPal blocks writers. Other processes face the core's 60 second file-lock timeout; same-process threads wait without a bound before that timer (`vendor/approval_receipt/filelock.py`). A core proposal would apply the same limit to the thread lock. The app takes its locks in one order everywhere (money lock, authority thread lock, policy chain lock), which removed the recovery-versus-authorization deadlock; hung PayPal still blocks threads until transport timeout. Whole-ledger rereads slow as receipts grow.
- Later FAILED refunds free order balance and are flagged; nothing resends or refunds another way.
- `python -m app` polls pending refunds once a minute through a background thread; no other scheduler.
- Arena fake PayPal forgets refunds on restart; signed receipts persist. Owner-held requests close immediately because no owner is online. The public arena allows 600 messages per hour through in-memory limits, shares one scoreboard, has no visitor sessions and stores messages in the host's decision log.
- USD refunds only; no payouts, MCP or sponsor tools. Simulation converts listed forms (€18.00, 18 GBP, 18 euros) at fixed demo rate values in USD: EUR 1.08, GBP 1.27, CAD 0.73, AUD 0.65 (`app/fx.py`). Screen, signed records and README label demo rates; all limits apply after conversion. Rates are unvalidated, untuned and not market rates; owners would set real rates. Since 2026-11-05, `--mode sandbox` converts nothing and holds other-currency messages (`FOREIGN_CURRENCY_HELD`). Real refunds require buyer currency, unsupported here; `OrderBook.load` rejects non-USD merchant orders. G12 holds unsupported currencies, codes beside dollar figures and two-currency messages. Unsupported-currency orders get no proposal/amount card; buyer and owner see person-review status. The short English currency list misses unknown terms. Reading amounts still requires a dollar sign, listed sign/code or “dollars”.
- Accessibility includes labels, focus rings, live regions, skip link and 48 pixel phone targets, 44 on wider screens. No screen-reader audit. Chrome headless checks from 2026-10-24 (`qa/browser-pass-2026-10-24/`) cover console errors, failed requests, overflow and labels, exiting non-zero on unexpected findings; they do not assert each page's business outcomes. No Safari, Firefox, real phone or screen-reader testing.
- No performance/load testing or compliance claims.
